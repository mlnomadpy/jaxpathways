## New sharded-training execution evidence

Reference command:

```bash
python3 projects/sharded-training/tests/check.py --implementation solution --stage all --output projects/sharded-training/outputs
```

Stages 1–4 passed on JAX 0.9.2 / NumPy 2.4.4 with four logical CPU devices. The test varies seeds 17/29/31/37 and batches 7/10/1/64 over 23 examples, then uses a separate 1,023-by-64 timing fixture. Actual valid partition counts include `[2,2,2,1]`, `[1,1,0,0]`, `[3,3,3,1]`, `[1,1,1,0]`, `[1,0,0,0]` and `[6,6,6,5]`. Each gradient matches a full-batch NumPy calculation and a partition-numerator/count reconstruction. Three `all_reduce` operations appear in the actual lowered StableHLO.

Two independent fresh subprocesses reproduce future sample IDs, losses and every state field after crossing multiple epoch boundaries. Observed final-weight error after complete restore is zero for both recovery fixtures. Resetting momentum/cursor/key separately yields errors of approximately 0.33990/0.04003/0.06173 for seed 17, batch seven, and 0.12765/0.09380/0.17282 for seed 29, batch ten. Missing momentum, corrupt permutation, mismatched configuration and duplicate checkpoint destinations are rejected.

The measured report stores compilation separately from eleven synchronized warm samples per eager-four, compiled-four and compiled-one-device variant. The compiled single-device reference matches the independent global gradient and four-device results. Four actual traced transitions produce XPlane and Perfetto files, from which the checker reads the named preparation and update durations. The README explains every panel and the timing boundary. Exact values, source hashes, device metadata and trace paths live in `projects/sharded-training/outputs/audit.json`; unlike correctness fixtures, timings are expected to change on rerun.

New project integration metadata: add `projects/sharded-training/project.json` to the project registry; map recovery/performance/distributed phase projects to this ID with the phase-specific stage descriptions above; add its cumulative checker (`--stage all`) to project validation; preserve its explicit prerequisites and `scale` assessment link. No shared manifest or other project was modified by this audit author.

Final local verification also checked both implementation/checker hashes against the fresh receipt, compiled all three Python source files, observed the scaffold fail at its first `NotImplementedError`, and visually inspected the actual three-panel PNG. The final warm medians were 421.46 ms (eager four), 0.1661 ms (compiled four) and 0.07225 ms (compiled one). Compilation was 33.90/28.76 ms for four/one devices. The plot and README explicitly explain that compiled four-device execution is slower than compiled one-device execution on this local fixture. No hardware-scaling claim follows.

Additional audit verification: `python3 projects/foundation-toolkit/tests/check.py --implementation solution --stage all` passed all four stages, including the fresh-process state replay. Current foundation and text solution/runner SHA-256 hashes both match their executed `outputs/report.json` receipts. The text checker was inspected here but not independently rerun by this audit author.
