# Independent TPU lesson review

Read-only review of the six TPU lessons against audit issues #74, #77, #78, #81, #82 and #90. Review scope was lesson JSON content, embedded code/build-step order, experiments, exercises and diagrams. Findings below are concrete mismatches or remaining acceptance gaps.

## Findings

1. **TPU-01 primary exercise and solution no longer match.** In `phases/19-tpu/01-get-a-tpu-running-and-verify-the-runtime/lesson.json`, `content.exercise` (line 135) asks for the 48 GiB / four-chip per-device ledger and a selected receipt with process count, JAX device count, physical chip count and topology/API identity. `content.solution` (line 136) instead lists single-host slices by aggregate HBM. It never calls the 48 GiB ledger helper or reports a receipt process count. The receipt builder (`content.code`, line 52) records `hosts_expected` as a constant but does not call `jax.process_count()` or observe physical-chip/API topology. Counterexample: the visible solution's `result` has no four-count comparison or selected-target process/device/chip row, so it cannot answer the exercise as written. The same 48 GiB calculation exists in a separate practice solution, but that does not make the primary solution complete.

2. **TPU-04 practice reads a nonexistent receipt key.** In `phases/19-tpu/02-bootstrap-venv-and-verify-tpu-runtime-receipt/lesson.json`, `content.practice[0].prompt` (line 100) requires `r['backend']`. `build_runtime_receipt` emits `observed_backend` (content.code, line 56) and no `backend`. Running the practice solution against the actual CPU receipt raises `KeyError: 'backend'`. Its fabricated `simulated_tpu` dictionary adds `backend`, which hides the mismatch.

3. **The TPU preflight scripts report failed target readiness as successful script completion.** TPU-01 and TPU-04 `content.code` (each line 56) compute `requested_target_ready`, but the main assertions only check `receipt['arithmetic_ok']`; the TPU-01 solution (line 136) likewise accepts arithmetic alone, and TPU-04 solution (line 95) only asserts arithmetic plus the closed-form sums. A CPU run in the supplied CPU environment printed `arithmetic_ok: true`, `requested_target_ready: false`, then exited successfully with “Verified runtime receipt” / “Runtime receipt”. A TPU backend with an unexpected device count has the same gap: arithmetic may pass while the launcher receives exit status zero. This contradicts the requested-target gate described in the sections and issue #77. Preserve CPU rehearsal by checking readiness conditionally when the requested backend is TPU.

4. **Both initial pinned-environment SCP commands target a directory they create only afterward.** TPU-01 `content.sections[3].commands[0].code` (line 66) and TPU-04 `content.sections[0].commands[0].code` (line 32) first copy `requirements.txt` to `~/jax-tpu-lab/`, then issue SSH with `mkdir -p ~/jax-tpu-lab`. On a new VM with no such directory, standard SCP cannot place the file in that nonexistent destination directory, so bootstrap stops before the mkdir. Create the remote directory first, then copy. The command is documented as an SCP transfer by [Google Cloud's `gcloud compute tpus tpu-vm scp` reference](https://docs.cloud.google.com/sdk/gcloud/reference/compute/tpus/tpu-vm/scp).

5. **TPU-06's target-trace command promises five steps, while the complete script defaults to four.** In `phases/21-tpu-systems/02-bfloat16-int8-precision-and-xprof-profiling/lesson.json`, the command label (line 38) says “capture a 5-step” trace, but `capture_warmed_trace` defaults to `steps=4` and the complete example calls it without an argument (`content.code`, line 52). A bounded CPU run confirmed the main script reports four profiled steps; only the reference solution explicitly runs three and five. Either pass `steps=5` in the command or change its stated count.

6. **TPU-03 retains an unrelated throughput equation in its memory-sizing section.** `phases/21-tpu-systems/01-tpu-generations-and-hbm-memory-budgeting/lesson.json`, `content.sections[0].math` (line 23), shows tokens/s from global batch, sequence length and step time. The section body discusses Roofline intensity and state/KV HBM ledgers, and its code calculates no throughput or step time. The displayed expression therefore has no defined/code-backed quantities in this lesson section; remove it or move it beside an actual throughput calculation.

7. **Issue #81's stable workload and quiz are corrected, but the lesson still lacks its requested timeline artifact.** TPU-06 now reuses the same bounded finite matrix, checks finite outputs, labels CPU versus TPU, and states that no collective is present. The quiz matches those limits. However, the lesson's only `content.visual` is the precision-error bar chart; `capture_warmed_trace` only returns a file count and timing, and no code extracts event names or produces the requested retained event excerpt/timeline. Learners are told to inspect XProf without an example event sequence or readable timeline to interpret. This remains an acceptance gap for #81, not a mismatch in the fixed-input arithmetic.

## Checks and evidence limits

- Executed the complete TPU-01 and TPU-04 lesson code and solutions in `/private/tmp/jaxpathways-0170-clean-learner-env/bin/python` with `JAX_PLATFORM_NAME=cpu`. Both finished successfully while their receipts correctly said `requested_target_ready: false`; this confirms finding 3. Executing the TPU-04 practice solution against its real receipt reproduced `KeyError: 'backend'`.
- Executed TPU-03 and TPU-06 main code and exercise solutions on CPU. TPU-03 produced the stated 7B mixed-state estimate of 117.347 GiB; its v6e-4 versus v6e-8 per-device ledger assertions passed under the expressly ideal-sharding and 8 GiB activation assumptions. TPU-06 produced the corrected storage ledger (BF16 32,768 B, INT8 codes 16,384 B plus 256 B scales, 65,536 B FP32 dequantized workspace) and finite 3-/5-step traces. The main TPU-06 script reported 4 steps, confirming finding 5.
- TPU-02 launch/state-resume and TPU-05 multi-host logic were reviewed statically; I did not run multi-host or TPU commands. No TPU VM was provisioned, no Cloud resource or paid workload was launched, and no physical-chip, target-topology, XProf TPU, or peak-HBM claim was qualified. CPU receipts only establish the CPU arithmetic fixture.

## Follow-up resolution check (2026-10-27)

I rechecked the TPU changes after the follow-up edits. Findings 1, 2, 4, 5 and 6 are resolved in the current source: TPU-01's primary solution now answers the requested 48 GiB ledger and selected-target receipt fields; TPU-04 practice reads `observed_backend` and handles missing keys; the pinned-environment and exercise SCP steps create `~/jax-tpu-lab` before copying; TPU-03's memory section now presents the per-device state and usable-HBM equations; TPU-06 explicitly calls `capture_warmed_trace(steps=5)` and retains its five-step caption. TPU-06 links the retained event example in performance-03, satisfying the #81 example requirement with the scope stated below.

The readiness gate now behaves as intended in CPU rehearsal and target-required launch mode. I executed the complete TPU-01 and TPU-04 embedded code, primary solutions, and both practice solutions with `/private/tmp/jaxpathways-0170-clean-learner-env/bin/python` and `JAX_PLATFORM_NAME=cpu`. Each completed with arithmetic true, backend `cpu`, one device, `requested_target_ready: false`, and `source_sha256: null`; the TPU-04 practice helper accepted the real receipt without a missing-key exception. I also ran each saved verifier with `TPU_REQUIRE_TARGET=1` on CPU; both exited 1 with `Requested TPU target is not ready: expected TPU backend and exactly 4 JAX devices`. An additional inline `python -c` run with `TPU_REQUIRE_TARGET=1` and no `__file__` exited 1 with `requires a saved verifier script with a readable source identity`. Interactive execution reports unavailable source identity explicitly rather than fabricating one. These checks establish only CPU behavior, not physical TPU readiness.

Two TPU-04 primary-solution details remain incomplete. `content.exercise` asks the learner to assert `requested_target_ready` only when backend is TPU and `device_count` is exactly four, but `content.solution` only asserts arithmetic and the oracle values, and only checks readiness false for CPU. A TPU run with the wrong device count would therefore not be rejected by that solution. The same solution labels the four- and eight-device oracle values as “4-chip” and “8-chip”, although its helper is parameterized by device count; these labels should say devices. The practice prompt and solution correctly use four-device terminology and the actual receipt keys.

The linked #81 example is a retained CPU timeline with real event timestamps, nested spans, and a changed injected wait, not a TPU trace from this lesson's dot-product workload. It teaches event accounting and counter interpretation, while requiring learners to inspect the backend and events from their own trace. No claim about TPU event names, lanes, or timing is qualified by this review.
